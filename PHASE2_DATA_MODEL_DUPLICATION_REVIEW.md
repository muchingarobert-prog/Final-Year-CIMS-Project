# Phase 2 Data Model Duplication Review

## User committees and CommitteeMembership

`CommitteeMembership` is the active membership relationship. Committee APIs, committee member/leadership views, dashboard counts, and authentication dashboard statistics query `CommitteeMembership` and its `is_active` field.

`User.committees` is a separate many-to-many relationship used by the user directory's committee summary and by announcement and event notification recipient selection. It is not maintained by the committee join/leave endpoints, so it can diverge from `CommitteeMembership`.

Recommendation: make `CommitteeMembership` the future source of truth, then migrate the announcement, event notification, and user-summary queries to it. Removing `User.committees` would require a data conversion and migration; it should not be removed during Phase 2.

## Event attendees and EventRegistration

The `Event` model has no separate `attendees` relationship. Attendance for events is represented by `EventRegistration`, with a unique `(event, member)` constraint. Event counts, attendee lists, registration actions, and cancellation all use `EventRegistration`.

There is no event-attendee duplication requiring schema work. The existing database uniqueness constraint prevents duplicate registrations; the registration action uses `get_or_create` to preserve that behavior under normal concurrent requests.

## Other observed relationships

Attendance uses `AttendanceRecord.member` and `AttendanceRecord.session` as its source of truth. Committee membership uses the duplicated pair described above. Notifications use `Notification.recipient`; they are generated by model workflows and are now not client-assignable through the API.

No model or migration change is required for the Phase 2 authorization work. Schema consolidation should be a separately reviewed migration project after dependent queries and existing data are inventoried.
